# WAMの予測で「待つ／進む」を判断する接続

**WAMの予測をmissionOSへ渡し、同じVLAの前進候補を選ぶか、待つかを切り替える接続を実装しました。CPUの代替予測・代替判断による検証であり、実WAMによる荷下ろし待ち飛行はまだ未達です。**

役割は次の順序です。

1. VLAが短い移動候補を出す。待機は別の候補として常に用意する。
2. WAMが、待つ場合と移動する場合の結果を予測する。
3. missionOSが予測と任務の状況を見て候補を選ぶ。
4. 承認範囲と最新の安全条件をRulesが確認し、APが実行する。
5. 実際の移動・荷下ろし・受領を別の観測で確認する。

今回実装・確認したのは予測の受取りから候補選択までです。VLA自身が
「待つ」を出せなくても、missionOSは前進候補を選ばずに待機できます。
前回のVLA単独診断の1/3という結果は保存し、この接続の合格条件にはしません。

| CPUで与えた条件 | 観測した結果 |
|---|---|
| 現在は空いているが、進むと区間内で接近が起きる予測 | 待機候補を選択 |
| 同じ現在観測・同じVLA候補で、予測のみ空き継続へ変更 | VLAの前進候補を選択 |
| 現在は占有中で、将来は空く予測 | 待機候補を選択 |
| 応答時には予測が行動終了までをカバーできない | 判断に使用せず再観測が必要 |
| 予測時刻の対応が未確認 | 判断に使用しない |
| 観測の版が変わった | 古い予測を拒否 |
| 保持できなくなった | 待機を選ばず、既存の機体側対処へ戻す必要あり |
| 海上工程 | モデル判断へ渡さない |

**8ケースで接続と拒否動作を確認しました。** 最初の2ケースは予測だけを
変えて選択が切り替わります。これは予測が判断へ届くことの確認であり、
実WAMの能力、飛行成功、待機時間短縮、学習効果を示す結果ではありません。
機体側の対処や再観測自体も、この検証からは実行していません。

既存の[実VLA・WAM画像](../yokohama-pad-native-probe/REPORT-ja.md)の
入力・出力の結び付きを再検証しました。画像は生成されていますが、先行機の
占有・退出を読む処理と、実時間に対応した動的予測の検証がありません。
空が多く既存の深度照合条件を満たさない問題も残っています。
そのため既存画像を「未来には空く」と読み替えて採用していません。

次は、同じ待機地点から先行機の荷下ろし・退出・退出中断・再占有を時刻付きで
記録し、WAMの予測を占有判断へ変換する部分を検証します。追加学習の対象は
その結果から決めます。学習する場合は別の動作・開始時刻を評価用に残します。
画像の完璧さや理想的なRulesを超えることは目標にしません。

追加GPU利用・追加学習はありません。今回の追加GPU費用は **$0**、
前回までの累計概算 **$17.37 / $20** のままです。
