## 何が動いたか

自機はPX4のAPで動きます。先行機とその荷下ろしは、別のGazeboモデルを台本で動かしています。先行機は自律飛行する2機目のPX4ではなく、荷下ろしも物理的な把持・解放機構の検証ではありません。自機の50 g貨物については既存の独立した受領検証を使っています。

機体はパッドから離れた既存のD3で保持し、占有を報告しました。MissionOSのCPU代替判断が「待機」を返し、機体がAP保持を継続。その後、観測した先行機の位置からパッドと進入経路が5秒間空いていることを確認して再照会し、「進入」の提案を受けました。最新の占有・機体状態・残量を機体側が再確認してから、承認範囲内のAP進入を実行しました。提案・許可・移動開始・受領・帰船は別の記録です。

**占有判定にはGazeboの位置情報を使い、判断は決定論的なCPU代替処理です。画像認識、実VLA＋WAM、追加学習は未実施です。** 先行機の台本や未来の退出時刻は判断側に渡していません。この回はモデルの価値を測る比較ではありません。

動画の配送先カメラは状況説明用です。実VLAの機上入力で占有・荷下ろし工程の違いが十分に見えるか、WAMの短い予測時間と実行時刻が合うかは、次に別途確認します。完璧な精度や理想的なRulesへの勝利を求めず、まず判断を更新して配送できることを目標にします。

## 不成功の試行も保存

最初の一往復試行は、占有報告と待機指示の後、先行機の位置変更に対する通信応答を得られず停止しました。配送・帰船は未達です。その後の短い単体確認では、応答と位置反映の時間差、応答欠測があっても位置変更が適用されることを観測しました。途中の補助確認には初期時計未受信と、厳しすぎた応答再送回数による停止もあり、保存しています。

修正版は応答欠測だけで進捗を判断せず、実際の位置で占有を判定します。変更要求は同じ位置に再送できるものだけに限定し、90模擬秒／180実秒の待機期限を維持しました。修正版の一往復では応答欠測の開始を7回記録しています。自機の保持・安全距離・残量・受領確認の条件は緩めていません。[試行一覧](attempts.json)

## 風で困ったときにMissionOSへ相談する

既存のMission Assuranceへ、機体からの状況報告を接続するCPU代替テストも追加しました。6場面すべてで、提案と実行権限を分けた応答を確認しました。[記録](wind-response-fixture.json)

- 海上では、経路・風に対する到達可能性・残量・到着場所の空きが確認された承認済みの退避先を提案します。陸地だけに固定せず船も候補にします。
- 陸上では、保持できると確認された場所での待機を提案します。
- 風が収まっても、機体の安定、経路、残量、期限を再確認するまでは再開しません。
- 通信を待てない状況は、機体側に事前設定した対応が受け持ちます。中央への照会を理由に、海上で無期限に待つ指示にはしません。

この風対応は、到達可能性などを仮定した**判断接続のCPUテスト**です。強風中に実際のAPを退避させる接続、通信断時の実機動作、風が収まった後の飛行再開は未検証です。以前の約9.15 m/sで再保持できなかった結果は変わりません。今回の配送は無風です。

## 再検証

`3545 passed, 2 skipped, 3 warnings in 125.12s (0:02:05)`。加えて、実際のPX4/Gazebo飛行、実ファイル通信、独立した受領判定と以下の検証を実行しました。

```sh
python scripts/yokohama_sitl.py --phase flight --approve-sitl --output-dir RUN \
  --sea-round-trip --deliver-payload --occupied-pad --timeout-seconds 2400
python scripts/verify_yokohama_pad_queue.py RUN --output RUN/pad-verification.json
python scripts/verify_yokohama_sitl.py RUN --output RUN/verification.json
python scripts/verify_yokohama_payload.py RUN --output RUN/payload-verification.json
python scripts/check_yokohama_mission_response.py --output NEW-wind-response.json
```

全飛行、占有待機、貨物の各検証は合格し、所有コンテナーを削除済みです。飛行時のソースを固定・保存しています。その後、ホスト側の停止処理が例外を返しても他の後処理を続ける保護を追加しました。この例外経路の保護を含めた全飛行の再実行とは扱いません。サンプリングした距離と接触ログの確認であり、連続的な無衝突・実機耐風性能を証明するものではありません。海上ではモデル推論・ウォームアップともゼロです。残量はSITLの時間ベース値で、Whや推論電力を測定していません。
