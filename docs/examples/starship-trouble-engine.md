# Starship trouble engine

Starshipの実飛行で報告された異常を手がかりに、6DOFシミュレータへ故障を発生させます。同じ乱数シード・設定・ソース・数値環境なら、同じ故障条件を再実行できます。機体の位置や姿勢を成功・失敗の状態へ書き換えず、故障後も運動方程式を積分します。

2026年10月13日にSpaceX・FAAの一次資料を確認し、統合飛行試験のFlight 1〜14を調べました。確認できた20件の異常について、起きたこと、公表原因、その確度、出典、現在のモデルで扱える部分を[カタログ](../agents/starship-incident-catalog.json)に保存しています。予定した着水、意図的なエンジン停止試験、地上試験は区別しています。

| ランダムに発生させる故障 | シミュレータに起きること | 参考となる実飛行 |
|---|---|---|
| 上昇中のブースターエンジン停止 | 1基の推力が失われ、分離後も故障を継承 | Flight 1、12、14 |
| Shipエンジン停止 | 1基を使用不可にし、残る推力・姿勢制御で飛行 | Flight 7、8、12、14 |
| ブースター再始動不良 | boostback開始時に1基を使用不可にする | Flight 2、3、7、8、11〜14 |
| RCSの一方向の能力喪失 | その方向の噴射対が使えなくなり、角運動へ影響 | Flight 3 |
| 放出機構の不具合 | コマンドが受理されても剛体ペイロードが分離しない | Flight 9のドア・放出不成立を抽象化 |
| タワーの健全性異常 | 現在の観測でタワー利用不可を通知 | Flight 6 |

火災、配管、熱防護材の焼損、構造破断の過程は解いていません。上表は、それらの一部の**結果としての能力低下**を試すモデルです。発生率、対象部品、時刻、故障の持続は試験用の仮定です。実機の故障確率や各飛行の完全な再現を意味しません。フラップ固着も明示指定で試せますが、確認済み史実との対応がないため既定の抽選から外しています。

## 実行

CPUのみで動き、モデルAPIや実機は呼びません。数値依存関係は
`pip install -e ".[spaceflight-qualified]"` でそろえられます。出力先は毎回新しくしてください。

```sh
python scripts/run_starship_trouble.py --approve-simulation \
  --seed 14 --max-events 2 --nominal-probability 0.2 \
  --output-dir output/trouble-seed14
```

まず短い試験をする場合：

```sh
python scripts/run_starship_trouble.py --approve-simulation \
  --seed 14 --family ascent_engine_out --nominal-probability 0 \
  --duration-s 180 --output-dir output/trouble-ascent14
```

- `manifest.json`：実行前に固定した故障予定。評価側だけが持つ情報です。
- `study.json`：実際の機体状態と故障の適用記録。
- `verification.json`：予定と適用時刻、エンジン状態、分離時の継承などの照合。
- `summary.json`：実際の終了理由と、発生しなかった故障。
- `report.html`：保存状態を使った3Dリプレイと故障発生イベント。

同じ故障予定の再生には `--seed` の代わりに `--manifest output/trouble-seed14/manifest.json` を使います。計算を途中で打ち切ったり、その飛行段階に到達しなかった場合、予定した故障が起きないこともあります。それを無理に発生させたり、再抽選したりはしません。

## MissionOSとの接続範囲

現在は、**MissionOSの実モデル判断と別プロセスの実6DOFへ接続済み**です。専用の承認付きCLIで、Jevが監視し、必要ならDeepSeekへ検討を渡します。追加診断、放出見送り、帰還抑止を選び、独立した範囲チェックと後続観測まで記録します。既存M3のチャット/Gateway便とは別の実験経路です。故障なしの帰還証明書は故障便に流用しません。

観測用APIは、現在時刻のエンジン・舵面・放出装置・タワーの状態だけを返し、シードや次の故障予定を含めません。ただし現段階の健全性信号は、故障を直接示す理想化した合成診断です。実機のセンサー誤差・遅延・誤報の再現は今後の接続で扱います。

故障に対するAI管制の評価は、発見、確認、計画更新、独立チェック、実行後の確認を担えたかで行います。シナリオに組み込まれたRulesとの得点差を、AIの価値の判定に使いません。

## 保存した試験結果

6種類の故障、正常条件、明示指定のフラップ固着について、実際のCLIと6DOF計算を通しました。各記録の検証は通過していますが、短い試験の時間切れや、フラップ固着後の衝突も結果として残っています。

さらに、事前に決めたシード `20261013` の通し飛行では、ブースターの再始動不良が1件発生しました。Shipは26基を放出しましたが、ブースターは約156.3 m/sの対地速度で接触し、回収基準を満たしませんでした。成功するまで引き直した結果ではありません。

[条件・ソースのハッシュ・結果の要約](../assets/starship-trouble-engine-20261013/summary.json)を保存しています。同じ放出不良の予定を最終コードで再生し、機体状態・放出結果・故障記録の完全一致も確認しました。

故障を入れない既存の帰還試験も39条件を最終コードで再実行し、全条件で従来の機体状態・結果との完全一致を確認しました。[照合記録](../assets/starship-trouble-engine-20261013/qualification-refresh.json)を残しています。これは通常飛行を変えていないことの確認で、故障後の帰還を保証するものではありません。

## ランダム故障と実モデルを一続きにした試験（2026-10-14）

`seed=20261014`、既定の6種類、最大2件、正常確率20%、800秒で事前固定し、1回だけ実行しました。故障の種類や時刻を見て選び直していません。

| 時刻 | 実際に起きたこと・AIの選択 | 後続確認 |
| --- | --- | --- |
| T+71.832秒 | 上昇中にエンジン1基が停止。その後の観測を受けたJevが継続を選択 | 運動を継続し、軌道条件に到達 |
| T+490.604秒 | 放出装置の詰まりが発生 | 現在の合成診断に反映 |
| T+490.854秒 | Jevが残りの放出を見送る | T+491.104秒にシーケンサーの見送り・放出0基を確認 |
| T+610.604秒〜628.104秒 | JevがDeepSeekへ渡す。DeepSeekは高度・速度・角速度・燃料・詰まりなどの根拠IDを返して継続を選択 | 10個の根拠IDと判断時の値を照合し、T+628.354秒に継続を観測（理由の全文を検証したものではない） |
| T+730.854秒〜737.604秒 | Jevが同じ診断を3回取り直して見送りを維持 | 3回とも2秒後の診断を完了 |

Jevは18/18回、DeepSeekは1/1回で有効な応答でした。判断に代替動作は使われず、記録と操作後の確認は通りました。DeepSeekの表示文は外部に返された判断要約で、隠れた推論ではありません。

**回収成功の試験ではありません。** Shipは0基放出・26基保持のまま800秒の軌道上で終了し、帰還は未解決です。ブースターは約154.43 m/sの接触点速度で衝突し、回収基準を満たしていません。今の故障用の権限は放出・帰還の抑止と観測に限られ、ブースターの帰還方式を変更できません。この失敗も保存しています。READMEの120秒動画は別の、ランダム故障を入れない回収判断の飛行です。

[今回の判断・観測・終了状態・ハッシュ](../assets/starship-trouble-control-20261014/summary.json) · [過去の失敗と修正後の試験](../assets/starship-trouble-control-20261013/summary.json) · [権限と検証の契約](../agents/starship-trouble-control.md)

通常条件の180秒CLI試験も別に実行し、モデルAPIなしで承認・別プロセス・後続観測が通りました。live実行では、Secret Managerから読み込んだ鍵をホストだけが保持します。まず `--prepare --mode live` で設定を固定し、その計画ハッシュを `--approve-plan-sha256` へ渡します。DeepSeekモデルはホスト設定で `deepseek-flash` を明示し、呼出し回数上限は置いていません。
