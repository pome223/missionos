# WAM追加実験のCPU事前検証 — 2026-09-25

現在の「待つ／常に通れる迂回路を使う」という条件では、WAMを追加する前に
単純な残り時間ルールで予算内到達の上限まで達しました。この条件での追加GPU
実験は見送ります。これは合成条件の計算結果で、実際の配送成功率ではありません。

評価用192条件の結果です。開発用192条件とは観測位置・速度などを変えています。

| 方法 | 予算内に到達できる条件数 |
| --- | ---: |
| 既存の停止予測ルール | 103 / 192 |
| 既存の等速予測ルール | 107 / 192 |
| 開発条件で選んだ固定手順：20秒待って迂回 | 112 / 192 |
| 迂回が残り時間内なら迂回、それ以外は待つ | **134 / 192** |
| 未来を完全に知り、処理待ち時間もない理想的選択 | **134 / 192** |
| 理想的選択でも、処理のため41.19秒待つ場合 | 56 / 192 |

残り58条件は、この候補のどれを選んでも予算内に到達できません。除外せず
分母に残しました。単純ルールは既存の停止予測ルールが到達可能な103条件を
すべて保ち、31条件を追加で予算内に収めました。実機への採用は未検証です。

所要時間には少し余地があります。処理待ちがゼロで未来を完全に知れば、到達可能な
134条件で平均5.15秒短縮できます。ただし同じ観測から異なる未来が起きる条件も
含むため、これは実現可能な予測性能ではありません。同じ入力には同じ手順を選ぶ
という制約を課した理想的選択では、改善の上限は平均1.06秒でした。

前回のANWM実測に基づく41.19秒の処理待ちを仮定すると、完全な未来情報が
あっても78条件で到達可能性を失い、両方で到達可能な56条件でも平均22.19秒
遅くなりました。今回はモデルを動かしていません。この時間換算は機体を待機させ、
実時間とミッション時間が同じ速さで進む場合の感度分析です。

CPU用の再現コマンド、条件固定、比較表、入力境界の検査を追加しました。
関連テスト45件と実際のCLI呼び出しを確認済みです。GPU追加費用は0ドルです。
Step 2全体の達成、WAMによる配送改善、10機運用、実機飛行は示していません。
