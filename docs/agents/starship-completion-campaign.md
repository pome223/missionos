# Starship completion gates and public evidence boundary

All four completion milestones remain unfinished. Public source/fixtures and
recorded derived media demonstrate numerical/runtime interfaces, not a completed
Starship return-and-catch mission. Historical failed development continuations
are not fresh-start robustness cases or evidence of learned model value.

## Fixed acceptance contract

A launch-derived return must retain the actual separation state, profile,
physical coefficients, actuator states, faults, and carried controller history.
Control requests act only through finite engines, TVC, RCS, and panels. Do not
project reference position/velocity/attitude into physical state, add fuel,
change the origin/horizon to fit an outcome, or relax arrival/support gates.

At one actual simulated time, all material-pin position, height, relative
horizontal/vertical velocity, tilt, Body-X/East clocking, body-rate, and support
fuel-reserve conditions must hold. Only then may a separately declared catch
invocation continue the exact state through finite arms/contact/support.
A static screen, forecast, favorable pose, record PASS, or ACK is insufficient.

## Four milestones

| Stage | Required evidence | Current boundary |
| --- | --- | --- |
| 1: constrained return/catch | Actual simultaneous arrival + reserve, then exact-state finite support | Unmet; launch-derived catch remains negative |
| 2: fresh-launch robustness | Frozen nominal and fault/wind/latency cases with actual continuous outcomes | Incomplete; development continuations do not substitute |
| 3: MissionOS operating comparison | Fresh observations, scoped proposal/approval, current Rules, one site choice, later effects, same-start Rules comparator | Deployment skip has a bounded operating slice; qualified tower capture/divert application is absent |
| 4: operator mission workflow | Explicit approval/action/observation records and a common-clock 2D/3D view of the complete qualified mission | Basic fixture console/replay is present; full catch workflow is unfinished |

## Negative development result

The [historical coupled-pin summary](starship-coupled-pin-trial-18.md) records
one 60-second, 600-step numerical continuation from a saved launch-derived
booster context. It remained aloft, never met all eight conditions, and ended
with 3.569 t fuel below 6.918 t required reserve. Fuel cannot increase in this
plant; that suffix cannot qualify by extending it. This is a specific failed
route/suffix, not a proof of global vehicle or guidance infeasibility.

Private run stores, raw traces, approval keys, and ignored local runners are
not shipped. Reviewed derived display data and media are separate from public
self-contained source/fixture reproduction. A historical verification is not
reissued under later changed producer/checker hashes.

## Missing joint guidance contract

A further route needs an implemented and validated joint trajectory/control
solver for the actual booster: 155 continuous entries (14 rigid-body/propellant,
three finite actuator states for each of 45 engines, and six panel angles),
plus carried controller/discrete memory. It must bind the exact start and
unchanged dynamics/mass-flow convention; finite startup/shutdown and discrete
engine modes; positive reachable force and simultaneous moment; fuel/rate/
intermediate hull constraints; material-pin terminal conditions; and a closed
solve/runtime budget. Predicted trajectories must be reintegrated through the
ordinary plant and independently checked, never copied into its state.

[Free-ignition constrained 6DOF descent](https://arxiv.org/abs/1811.10803)
and [NASA time-varying mass properties](https://ntrs.nasa.gov/citations/20230017074)
motivate constraints, not identified SpaceX parameters. No implemented wrapper
here satisfies the full joint-solver contract. Simplified SCvx examples do not
supply its convergence, realtime, or engineering-validity guarantee.

## Tower authority preparation

The actor/broker/SQLite one-use boundary, stale/late rejection, signed local
scope, and reducing-only worker guard have fixtures. The tower driver/verifier
modules are absent and the mission catalog does not activate a physical return
site. Preburn path qualifications are caller assertions until independently
bound to actual same-origin/site-neutral evidence. The alternate site is a
synthetic model-test site, not a cleared ocean operating area.

Future activation requires two genuinely qualified paths from the same
actual context, a site choice before the first site-specific command, current
Rules/default only if the default path is qualified, and later physical-model
effect verification. The existing early-return activation phases differ from
the preburn fixture; a reviewed typed integration must reconcile them.
An immutable child-owned execution watchdog and graceful terminal receipts
must survive host loss before driver activation. Same-OS-user signing keys are
software integrity, not cryptographic operator identity. Disk hashes do not
authenticate already imported code; two-second freshness is not a usability
or safety guarantee. Never renew approval or weaken freshness to mask this gap.

For the short public HTTP fixture and observed runtime boundary, use the
[chat contract](starship-mission-chat-contract.md#public-runtime-verification).
That fixture proves no catch, live provider value, or tower retargeting effect.
