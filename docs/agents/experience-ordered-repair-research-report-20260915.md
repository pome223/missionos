# 実測経験を使う修正手順の選択：公開研究レポート

2026年9月15日時点。本報告の問いは、MissionOSが保存した修正手順の成功・失敗を蓄積し、次の失敗で使う手順を変えることで、同じ試行予算の固定順より回復を増やせるかである。**同種の未使用シミュレータ状態20件では、固定順12件に対して経験順17件が完了し、5件の追加回復を確認した。** 一般の配置分布や実機での改善を示す結果ではない。

## 対象と判定

対象は本の配置作業に関する一つの失敗類型である。保存済みの基盤方策の動作prefixと修正手順を、CPUのロボットシミュレータで実行した。新しい基盤方策推論、GPU実行、有料呼出しは行っていない。試行は、支持・収容・直立・低速・接触解消・安定区間を満たし、保護対象と達成済み状態を維持したときに成功とした。別の公式タスク判定、実機の成功、別作業への転用はこの成功数に含めない。

各比較では、開始状態、候補、対照、各手順の実行上限、群の抽出方法、採用条件を結果を見る前に固定した。未使用群の正解となる手順や終端結果は、その群の試行順を作る入力へ渡していない。開始状態を再現できない試行、結果不明、保護条件の損失は成功にも失敗にも都合よく振り分けず、別に数える。

## 静的な使い分けから、直接測る方式へ

最初は、過去に成功した手順の適用条件を実測経験から学び、親版の完全な手順をfallbackとして保持した。開発状態では、過去版のどれかが解けた状態を維持しながら成功数が増えた。しかし、fitに使っていない状態では追加回復がなく、過去または親版の成功を失った。いずれの候補も採用条件を満たさず、全面置換していない。

| 固定比較 | 開発状態の親版 → 候補 | 未使用状態の親版 → 候補 | 採用結果 |
| --- | ---: | ---: | --- |
| 第1比較 | 101 → 107 / 116 | 11 → 11 / 16 | 過去成功を3件失い、棄却 |
| 第2比較 | 112 → 121 / 132 | 8 → 8 / 16 | 追加回復1件、親版退行1件、過去版のみ成功した1件の退行で棄却 |
| 第3比較 | 120 → 131 / 148 | 11 → 9 / 16 | 親版成功を2件、過去版のみ成功した1件を失い、棄却 |

近い二つの開始状態で、同じ保存手順を選んでも一方は成功し、もう一方は失敗した。二状態で保存手順を直接実行すると、複合候補と要求動作列・終端結果が一致した。したがって、少なくともこの二例では手順を実行器が別動作に変えたのではなく、**手順の効果が開始状態に依存した**。過去の成功だけで新しい状態の結果を確定する静的条件には限界がある。

そこで、開始状態をresetして再実行できるシミュレータに範囲を限定し、過去経験を「試す順」に使う方式へ変えた。現在の親版を最初に実行し、失敗したときだけ、指定した数値観測を単位に合わせて正規化し、入口観測が最も近い**実測成功例**を持つ保存手順を上限1件試す。失敗や未試行は成功の証拠にしない。選択は手順名やLLMの説明ではなく、**同じ開始状態からの直接実行とVerifierの結果**で決める。保存手順が成功した場合は、別の同一状態実行で結果を再確認した。個々の評価例向けの修正コードや手動の分岐条件は追加していない。

## 事前固定した二つの未使用比較

最初の未使用16状態では、親版9件に対し、経験順と事前固定した保存手順の順はともに15件だった。この比較は直接測定による回復を示すが、**経験による順序の上乗せは0件**だった。

次は、開発状態148件のうち、親版と固定順の最初の保存手順が失敗し、別の保存手順が成功した5開発例をすべて中心にした。各中心と近くの親版成功対照を、事前に決めた位置差でずらして未使用20状態を固定した。中心を選ぶ際に使ったのは開発例の結果だけで、20状態の成否は抽出・試行順の決定に使っていない。親版と代替1件という予算、開始状態、成功・保護条件を揃えて比較した。

| 未使用群 | 親版のみ | 固定順で代替1件 | 経験順で代替1件 | 親版成功の退行 |
| --- | ---: | ---: | ---: | ---: |
| 最初の16状態 | 9/16 | 15/16 | 15/16 | 0 |
| 適格性を確認した20状態 | 12/20 | 12/20 | **17/20** | **0** |

後者では、親版と固定順の両方に対し5件の追加回復があった。追加回復は、経験順が選んだ保存手順を別実行で再確認した結果を含む。20状態の比較全体で結果不明0、保護・達成損失0だった。実Backend実行は41回、計6,835制御である。保存経験が試行順を変え、限られた代替1件の予算で有効な手順へ到達したことが、この比較で測れた付加価値である。新しい物理動作を自動生成した成果ではない。

## この結果の射程と公開実装

20状態は、開発例で固定順に弱点があり、別の保存手順に成功実績があると確認した失敗類型から選んだ。無作為な全配置分布ではなく、既知例の近傍を調べた比較である。別の固定順、代替手順を2件以上試す予算、異なる作業、実機、公式タスク判定まで優位と主張しない。また、シミュレータで同じ入口を再現できることが前提であり、観測factのdigestだけで隠れたシミュレータ状態まで同一と証明できるわけではない。

公開した[`empirical_repair_trials.py`](../../src/runtime/empirical_repair_trials.py)は、実測経験から有限の試行順を提案し、同じ入口に結びついたVerifier結果が成功を示した手順だけを提案する。承認・Rules・Executor・Verifierの権限は引き継がず、実Backendや実機を起動しない。公開用の抽出後も、20状態での提案順と判定は研究実装と全件一致した。公開fixtureの実行確認は次のとおり。

```sh
PYTHONPATH=.:packages/missionos-core/src python -m scripts.smoke_empirical_repair_trials
```

このfixtureは、親版失敗後に保存手順が直接成功したときだけ提案する経路、親版成功の維持、入口観測欠落の保留を確かめる。**上の20状態の実Backend結果をfixtureから再現するものではない。** 私有のraw episode、状態復元設定、保存prefix、ローカル実行器は公開リポジトリに含めていない。
