各方式1試行の開発比較であり、一般的な性能差ではない。未到達で着陸した側の短い距離・時間を効率向上とは解釈しない。停止は予定したチェックポイントで行い、供給済みの2経路から選んでいる。障害物は飛行開始後に挿入され、その後は静止したままである。

再観測側では連続時刻の条件を満たさなかった途中の12フレームを捨て、連続した16フレームを取り直した。これは同じ試行内で事前定義された撮影処理であり、飛行のやり直しではない。その待ち時間も37.212 wall sに含めた。採用時の最新観測は1.424 wall s前だが、判断全体が1.424秒で終わったわけではない。両方式とも速度0.2倍のシミュレーターを使用した。

WAM・Jev・GPU・事後学習は使っていない。今回の単純な深度方式が到達したため、この1ケースに到達数を改善するWAMの余地は残らない。常に左迂回する固定方策でもこの障害物は避けられるため、最良の固定方策への優位性も主張しない。確認できたのは、途中の観測を経路変更と到達へつなげる仕組みである。

## 分母と失敗の保存

最初の`pair01`は1試行を実施し、停止地点での撮影を既存の離陸地点限定ガードが拒否した。安全に着陸・disarmして比較を中断し、もう一方は未実施である。[失敗記録](development-attempt-01.json)を保持した。

修正後の`pair02`はコードと条件を新しく固定して2試行を実施した。従って今回の開発作業全体は**計3飛行（初回失敗1、修正後比較2）**である。初回失敗を取り除いた成功率や、未使用条件での汎化性能は報告しない。R2の12例とは別の試験である。

## 再検証と表示確認

```sh
python scripts/verify_urban_reobserve.py "$RUN/frozen_route"
python scripts/verify_urban_reobserve.py "$RUN/reobserve"
python scripts/render_urban_reobserve_report.py --cohort "$RUN" --output "$REPORT"
python scripts/check_urban_reobserve_report.py docs/assets/px4-stop-reobserve-20260925/pair02
```

元記録の検証器は署名・観測時刻・深度からの選択再計算・別の安全判定・観測軌跡・停止滞在・着陸・disarm・削除を確認した。公開レポート検査はファイルハッシュ、集計と埋め込みデータの一致、有限かつ時刻順の表示点を検証する。公開検査だけで非公開の元飛行記録を再検証したとは扱わない。

動画は観測されたGazebo RGBをシミュレーション時刻に合わせて変換したもの。地図は約0.24 sim sごとに間引いた実測点と重要イベントを表示し、機体包絡余裕は間引く前の記録で算出した。ループバックHTTPで再生/一時停止、40秒への移動、動画と軌跡の同期、360px幅の折り返しを確認した。HTTPで配信する場合は動画のRange取得に対応するサーバーが必要。CodexブラウザーのURL制約により、`file:`での直接表示は未検証。

元記録はタスクのローカル出力フォルダーに保持する。公開物には鍵・承認参照・私用パス・タスクDBを含めない。通常Gatewayへの閉ループ接続、連続飛行中の緊急停止、任意経路生成、移動障害物予測、実機飛行は未実施。
