# MissionOS × Go2：Agent管制から配送完了までの技術検証

**検証日：2026年9月25日｜対象コード：`cf3db6c`｜屋内MuJoCoシミュレーション**

[English version](index-en.html)

MissionOSのGo2チャットでAgent管制を標準にし、依頼・承認・実行・模擬受領・帰還・終端確認までを接続した。一時的な通路閉鎖では、実際のDeepSeek応答が「10秒待つ」「経路を再計算する」を選び、Rulesの検査を通過した判断から走行が再開した。別の動く障害物の走行では、局所的な停止・再開を犬側の制御が処理し、LLMを呼ばずに配送を終えた。

この報告が示すのは、**判断・承認・制約・実行・検証をつないだ管制の動作**である。実機配送、カメラによる自律知覚、WAMの導入、単純なルールに対する性能向上を示すものではない。

### A. 動く障害物に道を譲る ― ご指定の動画

ブラウザ「犬さんに配送を頼む」で再生できる録画に対応する。画面の初期値は「MissionOS Agentが状況を判断」で、配送は87.390シミュレーション秒で完了した。ただし、この走行では例外判断をAgentへ上げる必要がなく、**LLM判断は0回**だった。動画内の `host Agent enabled` は設定の表示であり、推論実行を意味しない。

## 4. システム構成と責任の分離

```text
人：配送を依頼 → 計画・行動範囲を承認
              ↓
MissionOS chat / Browser → Gateway → Go2DeliveryMission
                                     ↓ 走行中断・例外観測
                         host Agent（DeepSeek）
                                     ↓ 行動案＋理由
                         Rules（最新状態と承認範囲を再検査）
                                     ↓ 許可された操作
                         Executor（待機／再計画／帰還）
                                     ↓
              既知地図A*＋方位フィードバック＋局所速度ガード
                                     ↓ 速度指令
                  RL-SAR歩行ポリシー → 関節目標＋PD → MuJoCo
                                     ↓ 観測
                      Verifier → 模擬受領／帰還／終端確認
```

**Agentは行動案を選び、Rulesが制約し、Executorが動かし、Verifierが結果を確かめる。** Agent応答そのものを承認・配送完了に読み替えない。

- **ミッション層**：最大3回の例外判断、合計20シミュレーション秒の明示的待機、同じ配送先への再計画、未配送での帰還、人への確認。通常のチャット入力は固定操作への対応で、無制限な自然言語ミッション生成ではない。
- **ナビゲーション層**：既知地図のA*、0.1 m格子、0.45 mの余裕、方位フィードバック。ROS 2 Nav2やUnitree Sport APIは今回呼んでいない。
- **局所回避層**：障害物位置のシミュレータ読出しと差分速度から、進行方向の競合を判定して譲り・再開を行う。カメラ知覚ではない。
- **歩行層**：RL-SARの学習済みTorchScriptポリシーをCPUで実行。IMU角速度、重力方向、速度指令、関節状態、前回出力から12関節の目標を作る。物理刻み0.005 s（200 Hz）、4ステップごとにポリシー更新（50 Hz）。関節目標をトルク制限付きPDで追従させる。

今回のAgentは `missionos_go2_supervisor_agent`、モデル識別子は `deepseek-flash`、呼出しはADK/LiteLLMのstandalone runner。VLAではなく、画像や関節動作を直接出すモデルでもない。SimDist、NavThinker、NWMを含むWAMはこの経路に組み込まれていない。

## 6. 動画B：実際のAgent判断と因果のつながり

| シミュレーション時刻 | 観測・判断・実行 |
| --- | --- |
| 9.005 s | 上下両通路を試験側が閉鎖。往路を中断 |
| 11.005 s | 停止後、`decision_1` 用の状態を取得。配送経路なし、帰還経路あり、施設通知は約10秒後の再開見込み |
| 16.215 s | Agentの `wait(10.0)` がRulesを通過し、待機開始 |
| 21.005 s | 試験側が通路を再開。地図revisionが更新 |
| 26.220 s | 待機後の新しい観測。配送経路あり。`decision_2` を要求 |
| 27.480 s | Agentの `reroute` がRulesを通過。承認済みの同じ配送先へ再計画 |
| 53.130 s | `source_decision_id=decision_2` の往路到着を検証 |
| 90.430 s | 模擬受領後、受付への帰還到着を検証 |
| 95.455 s | 5秒の終端保持を検証し、配送完了 |

Agentの主張の要旨は、1回目が「再開見込みと残り待機予算を踏まえ、待って再観測する」、2回目が「配送経路が利用可能になったので同じ目的地への経路を再計算する」。要求・応答のハッシュ、実呼出しフラグ、Rules結果、実行された移動のdecision IDを照合した。単にモデルが応答しただけでなく、2回目の判断から検証済みの往路到着へつながっている。

ホストの呼出し開始〜終了という壁時計区間は、1回目5.259115秒、2回目1.090103秒。これは記録された1走の応答時間で、モデルの一般的な遅延分布でも、純粋な生成時間だけでもない。IPC待ちや最新観測取得を含むシミュレータ側の停止区間とは一致しない。

また、11.005秒から26.220秒までの15.215秒すべてを「10秒の待機指示」と呼ぶのは誤りである。前半にはAgent応答を待ちながら姿勢を保つ区間があり、明示的な10秒待機は16.215秒から始まる。再開予定を施設通知として与えているので、WAMが見えない未来を推測した実験ではない。`reroute` は同じ目的地への再計算を意味し、長い別経路を選んだこと自体を示す識別子でもない。

## 7. 承認、Rules、停止、到着の契約

### 承認とAgent利用

CLI検証は、承認前の `/run` が拒否されることを確認してから `/approve`、`/run` を実行した。承認は配送先、シナリオ、入力ハッシュ、Agent設定、行動範囲に結び付く。Gateway上のホスト資格情報はシミュレータ子プロセスやブラウザへ渡さない。既定Agentの接続が未設定なら明示的に失敗し、黙って固定ルールへ切り替えない。

### 判断の再検査

Rulesは要求ハッシュ、観測ID、JSONスキーマ、許可アクション、有限な待機値と残り予算、理由の形式を検査する。さらに応答後の最新状態について、観測の鮮度、姿勢、領域内、ハートビート、キャンセル・安全違反・接触、原点からの位置ずれ0.25 m以内、地図revisionの一致を検査する。再計画には配送経路が利用可能であることが必要。条件が変化した応答は、古い正しい判断という理由で実行しない。

Agent応答待ちは1回あたり最大35壁時計秒の境界を持つ。保持中も物理ステップと姿勢維持を続ける。応答がない場合に無制限に待つ設計ではない。

### 到着修正と二つの許容距離

PRの到着修正は、移動Executorの目標許容距離0.25 mを緩めない。内側の0.7倍（0.175 m）を停止開始の目安とし、2秒保持したあと再観測する。0.25 mを外れた場合は元の時間予算内で補正し、キャンセル・保持中の接触等があれば補正走行を行わない。

これとは別に、ミッション計画の受領・帰還保持に使う距離許容値は保存計画で0.4 m。**移動完了の0.25 mと、ミッション検証の0.4 mを混同しない。** 帰還後は5秒の保持中に1秒ごとに状態を確認し、安全違反、領域逸脱、接触、キャンセル、位置範囲を検査する。

### 異常終了後の再実行

Gateway起動時は中断された配送に停止要求を出し、子プロセスに継承したファイルロックで旧ワーカーの終了を確認するまで新規配送を抑止する。単なるPID確認に頼らず、欠損・差し替え・旧形式の証拠は未確認として扱う。旧ミッションを成功に変更する機能ではない。

| 表示／操作 | 確認した内容 |

| `missionos chat` | Go2依頼、承認前拒否、承認、実行、完了状態 |
| チャット `/status` | 現在の配送タスクの状態 |

## 9. テスト・CIと確認できていないこと

対象改修ではPython 3.11の全2,715テスト、うちGo2関連76テストが成功。Python 3.11／3.13の公開CIも同じheadで成功した。接続未設定時の停止、表示上の「設定済み」と「実応答あり」の分離、Rules拒否の表示、HTMLエスケープも含む。単体テストの成功を配送完了の代替にはせず、動画BのCLI→Gateway→Agent→物理シミュレータの実行を別に確認した。

PRには、以前の `5953588` で行った固定ルール配送、譲り中のキャンセル、Gateway強制終了・再起動の検証も記載されている。これらは本報告の2本の動画や、今回新たに実行した試験として数えない。本報告作成時は既存記録を再検査し、新しいモデル呼出しや配送は開始していない。

未検証事項は次の通り。

- 単一地図・既知シナリオ・各1走であり、成功率、再現性、最悪遅延、安全性の統計的保証はない。
- 真値の自己位置・障害物情報に依存する。照明、遮蔽、誤検出、位置推定誤差、実機通信遅延を含まない。
- 模擬受領は論理イベント。積み下ろし、実荷物、実人との接触安全、実機走行は未検証。
- WAM、VLA、SimDist、NavThinkerの効果を検証していない。
- Agentと単純ルールの同条件比較がないため、費用・待ち時間・到着率の改善は主張できない。
- `map`は連続更新ではない。動画の3倍速、リプレイの観測周期、壁時計の推論区間は異なる。
- 公開PRのレビュー可能状態と製品全体のリリース受入は別。PX4/Gazebo、Nav2/TurtleBot3など全経路の受入はこの試験の範囲外。

## 10. 再現手順

対象は[公開PR #115](https://github.com/pome223/missionos/pull/115)の[コード `cf3db6c`](https://github.com/pome223/missionos/tree/cf3db6c462db4cee9dd818f37b62af2011f09646)。[CI run 36136000626](https://github.com/pome223/missionos/actions/runs/36136000626)が対応する。MuJoCo 3.13.0、Torch 2.14.0は実行結果に記録された値。

外部のモデル・ポリシーは次の固定版。重みを本レポートへ複製していない。

- RL-SAR：`376d42c9b128f963ab08579762d5a216a976ce39`、`policy/go2/robot_lab`
- RL-SAR Zoo：`7dd30bdc7806898950b354260655d5a7f0ce844e`、`go2_description/mjcf`

キャッシュの準備・依存関係は[対象版の実行手順](https://github.com/pome223/missionos/blob/cf3db6c462db4cee9dd818f37b62af2011f09646/docs/agents/go2-indoor-delivery.md)に従う。以下の `VERIFY_ROOT` は新しい出力ディレクトリを指定する。既存証拠に上書きしない。

```bash
python -m pip install -e ".[dev]" -e packages/missionos-core \
  -e packages/missionos-cli -e packages/missionos-gateway

# DEEPSEEK_API_KEY はホスト環境で安全に設定しておく。
# 必要ならランチャーの既存Secret Manager参照を利用する。
RUN_MISSIONOS_GO2_DELIVERY_SIM=1 RUN_MISSIONOS_GO2_SUPERVISOR=1 \
MISSIONOS_JEV_MODE=off PYTHONPATH=. \
python scripts/start_go2_supervisor_gateway.py \
  --state-dir "$VERIFY_ROOT/gateway" --port 18851
```

別端末で、CLIの管制モード指定を省略して既定値を使う。

```bash
missionos --gateway-url http://127.0.0.1:18851 chat \
  --go2-scenario temporary_blockage 'Go2で会議室Aへ届けて'
# 同じチャットで /approve → /run → /status

# 検証を一括再現する場合（新しい推論・シミュレーションを実行する）
RUN_MISSIONOS_GO2_DELIVERY_SIM=1 python scripts/verify_go2_delivery_cli.py \
  --gateway-url http://127.0.0.1:18851 --scenario temporary_blockage \
  --supervision-mode default --require-agent-judgment \
  --output "$VERIFY_ROOT/agent-default"

# ブラウザで動画Aの場面を選んで依頼・承認・実行する場合
python scripts/open_go2_chat.py --gateway-url http://127.0.0.1:18851 --port 18852
```

個別の配送IDは依頼時に取得する。履歴・セッションを切り替える場合は明示的に管理する。ホストAgentの応答は再実行時に同一になる保証はない。


## 11. 公開資料と証拠の追跡

この公開版は一時サーバーやGatewayに依存しない。`index.html`、`index-en.html` と `media/` を同じ相対配置で保存すれば動画と記録再生を閲覧できる。本文は `report.md` と `report-en.md`、表示データは `data/replay.json`、確認用の結果抜粋は `data/results.json`。

[来歴記録](provenance.json)には対象コード版、元の結果・時系列ファイルのSHA-256、実行時ソースのハッシュを記録した。識別には公開用の場面名 `moving` / `agent` を使い、私有のrun ID、承認記録、タスクDB、生ログ、ローカルパス、資格情報は含めていない。元の観測点は間引かず、再生に必要な項目を抜粋した。動画は元の録画と同一である。

[公開ファイルmanifest](manifest.json)と[検証スクリプト](verify_report.py)で、公開ファイルの完全性、結果抜粋と表示値の整合、実行に結び付いた判断、相対リンク、日英の数値一致を確認できる。元の非公開ログはこの配布物には含まれないため、この検査を第三者によるシミュレーションの独立再実行とは呼ばない。元記録との照合は公開資料の作成時に行った。

2走の実行時ソースハッシュは対象コミットの該当コードと一致した。CLI走行時の未コミット変更は後に同コミットへ収録され、最後の書式整理はAST同値を確認した。元の証拠一式は別のローカル保存先で保持している。

## 12. 結論と次の検証

Agentの既定設定だけでなく、実際の判断がRulesを経て再走行・模擬受領・帰還に結び付くところまで確認した。同時に、動く障害物への短い譲りは、Agentを呼ばない局所制御の仕事として分離できている。

次に性能を評価するなら、**同じ閉鎖時間・通知・観測・行動範囲を与えた固定ルールとAgentを比較する**。再開見込みに従う単純ルールを強い比較相手とし、同条件で到着、未配送帰還、待機、壁時計遅延、推論費用を測る。まず最適に選び分けた場合の改善余地を確認し、差がない場面で推論を繰り返さない。本報告ではこの追加試験は実施していない。
