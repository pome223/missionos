# MissionOS v0.1.0-rc.1

Release candidate validated on 2026-07-22 against public commit
`159f68452a935d3ae86d6d17ea6a7765965592e2` before this release-note-only
commit was added.

## Candidate scope

- DeepSeek V4 is the primary hosted chat backend in the standard install.
- The public CLI and fixture Gateway support a credential-free HTTP smoke.
- TurtleBot3 house-floor-plan rendering uses `turtlebot3_house.v1`; the legacy
  simulated pillars are not part of that floor plan.
- PX4 recovery replay bundles can be exported, anonymized, and verified.
- Compound PX4 wind and obstacle recovery keeps over-limit wind in Safety HOLD
  and requires operator review instead of creating dispatch authority.

## E2E / Runtime Verification

A fresh clone of the public branch was installed into a new Python 3.13 virtual
environment with the README command:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e . -e packages/missionos-gateway -e packages/missionos-cli
missionos --help
```

`python -m pip check` reported no broken requirements. The documented fixture
Gateway smoke then exercised real loopback HTTP routes through `missionos
status`, `say`, `job-status`, and `map` for the same
`task_fixture_delivery`. The generated map remained read-only fixture evidence:

```text
status=fixture_only
actual_sitl_flight=false
delivery_completion=false
physical_execution=false
```

The TurtleBot3 house map was rendered from the committed public runtime and
floor-plan assets for a planned bedroom route:

```text
map_kind=indoor_local_xy
floor_plan_id=turtlebot3_house.v1
walls=32
pillars=0
destination_room_id=bedroom
planned_points=12
observed_points=0
physical_execution_invoked=false
mission_delivery_completion_claimed=false
```

The documented anonymous PX4 replay flow generated, exported, and verified the
fixture bundle:

```text
verification_status=verified
closed_loop_cycle_count=2
causal_form=Form 3
blocking_reasons=[]
delivery_completion_claimed=false
physical_execution_invoked=false
```

The compound-hazard PX4/Gazebo smoke for PR #38 additionally observed a
source-backed obstacle and over-limit wind in the same recovery epoch. MissionOS
selected `operator_review`, created no dispatch authority, and the operator
ended the smoke with an explicit LAND. This was simulator evidence, not hardware
execution or delivery completion.

## Publication checks

- No installed dependency or Python import refers to a private MissionOS
  repository.
- No tracked or historical private key, live-token-shaped secret, personal
  workstation path, or committed `.env` file was found.
- The deliberate fake API key in the replay source fixture was absent from the
  exported replay bundle.
- All 26 README links resolve, and the files referenced by the quickstarts are
  present.
- PR #38 passed its Python 3.11 and Python 3.13 checks before this
  release-note-only update.

## Limitations

- The fixture Gateway does not prove production LLM behavior, simulator flight,
  delivery completion, or physical execution.
- The house-map acceptance run renders a planned route from committed fixture
  geometry; `observed_points=0`, so it does not claim Nav2 motion.
- Hosted chat requires operator-provided credentials. TurtleBot3 Gazebo/Nav2
  execution remains an opt-in Docker simulator workflow.
- The second PX4 obstacle was materialized but not traversed because the first
  compound hazard correctly stopped the mission.
- Legacy `boiled-claw` identifiers remain in compatibility code and simulator
  service names. They are not private repository dependencies.
