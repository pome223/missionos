# MissionOS v0.1.0

MissionOS v0.1.0 fixes a small backend-neutral authority and feasibility core,
then proves it with two materially different simulator backends: PX4/Gazebo
and TurtleBot3/Nav2/Gazebo.

The release preserves this boundary:

```text
LLM judges.
Human approves.
Rules constrain.
Executor acts.
Verifier checks.
Repair loops.
```

## What is included

- Backend-neutral `HazardState`, `ActionCandidate`, and tri-state
  `ActionFeasibilityResult` contracts in `missionos-core`.
- The same Core conformance entry point for PX4 and Nav2 adapters. Core
  contains no backend-name branch.
- Deterministic anonymous corpora for both backends with exact
  `verified_feasible`, `blocked`, and `unverified` outcomes.
- Separate proposal, human approval, dispatch-time revalidation, dispatch
  authority, runner ACK, observed effect, and terminal observation artifacts.
- Fail-closed policy, telemetry, obstacle geometry, 3D clearance, payload,
  thermal, and source-freshness checks at the applicable adapter boundary.
- Read-only `chat`, `job-status`, `operate`, `watch`, and `map` projections for
  the same source Task.

## Limitations

- PX4/Gazebo and TurtleBot3/Nav2/Gazebo results are simulator evidence, not
  physical hardware evidence.
- No payload-delivery completion is claimed.
- Anonymous corpus replay invokes no LLM, ROS/Nav2, PX4/Gazebo, approval,
  dispatch, or execution authority.
- The house-map acceptance result is planned fixture geometry with
  `observed_points=0`; it does not claim Nav2 motion.
- Backend-specific evidence acquisition and geometry remain in runtime
  adapters. The Core defines shared contracts and invariants; it does not make
  all robot physics identical.
- Live hardware remains opt-in and requires separate actuator, E-stop,
  environment, and operational validation.
